# 修复方案：保留原始资料，重置处理结果

## 1. 目标与约定

修复 22 项正式问题，以及 3 项附加问题：MinIO 初始化入口、取消生成后的终态处理、切分幂等键复用。

按新项目开发处理：

- 保留账号、项目、成员关系、模型与各类处理配置、提示词及原始 PDF。
- 清空解析、清洗、切分、生成、审核、精修、数据集、评测集、任务和导出记录，以及对应派生文件。
- 页码以可信物理页面范围为准，跨页保留来源页集合，无法确认时显示“未知”。
- 完整使用流程由你手动验收；实施时执行必要的定向检查。
- 不增加历史数据兼容分支，不引入新的任务框架或审计系统。

## 2. 修复内容与顺序

### 第一批：恢复构建和基础配置

**CR-021、CR-022、MinIO 初始化入口**

- 固定 CI 的 Node/npm 版本，使用与 CI 一致的环境修复锁文件缺项，保持业务依赖版本。
- 将开发、测试和 CI 的镜像统一固定为：
  - `quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z`
  - `quay.io/minio/mc:RELEASE.2025-08-13T08-35-41Z`
- 两个镜像的 manifest 已确认可读取；服务端版本与本机现有缓存一致。这是恢复现有环境的历史版本选择，后续升级单独安排。[上游发行说明](https://github.com/minio/minio#distribution)
- CI 初始化命令显式使用 `/bin/sh` 入口，创建测试 bucket，并开启输出 bucket 的版本控制。

**CR-016、CR-017、CR-020**

- 注册查重改为存在性查询；数据库唯一约束冲突也转换为正常业务错误。
- 数据库连接地址使用 SQLAlchemy `URL.create` 构造，同步处理 Alembic 配置中的 `%` 转义。
- 各类默认配置切换统一取得项目行锁，锁后重新读取默认项，再清除旧默认、设置新默认。复用现有 TaskPolicy 的处理方式。

### 第二批：保护删除和上传路径

**CR-001**

- 文档删除先收集文件路径，再执行数据库删除并提交。
- 外键阻止删除时回滚并返回 `409 DOCUMENT_IN_USE`，不执行任何文件删除。
- 数据库提交成功后，清理 PDF、解析产物和清洗产物。
- 存储清理失败记录具体路径，避免把文件先删掉、数据库却仍保留记录的问题重新引入。

**CR-006**

- 保持现有 200 MiB 限制。
- 先利用 `UploadFile.size` 拒绝已知超限文件；读取时仍限定最多 `MAX_SIZE + 1` 字节。
- 超限返回 413，不进入 PDF 解析、存储上传或数据库写入。

**CR-018、CR-019**

- T09 回填统一使用 `.mappings()` 读取结果。
- 证据坐标优先在原始字符串中精确查找；需要 NFC 等价匹配时，将规范化位置映射回原文边界，并复核原文切片。
- 修正迁移代码，但不编写针对现有处理结果的历史修补流程。

### 第三批：修复候选审核和生成门禁

**CR-002**

- Candidate 增加 `content_revision` 和 `reviewed_content_revision`。
- 编辑、审核、提升请求均携带 `expected_revision`。
- 三条路径使用同一候选行锁，并在锁后刷新 ORM 状态、检查版本和提升状态。
- 编辑成功递增版本并清空审核；审核绑定当前内容版本；提升要求审核版本等于当前内容版本。
- 版本过期返回 409，前端保留编辑草稿，提示重新加载。

**CR-003**

- 证据 Chunk 必须属于候选来源批次冻结的 `selected_chunk_ids`。
- 使用历史批次自己的冻结集合判断，不根据当前 active ChunkSet 推断。
- 保留现有项目权限、字符范围和引用文本校验。

**CR-004**

- 批次创建时冻结有效输出 schema：任务类型的基础要求，加上模板配置的约束。
- QA 要求非空 `question/answer`；知识抽取要求非空 `title/content`；评测用例要求非空 `question/reference_answer`。
- 模板未配置 schema 时使用对应基础 schema；配置了无效 schema 时拒绝创建或更新模板。
- worker 在写成功状态、Candidate 和成功计数前执行校验。
- 非对象、缺字段或空白必填内容统一记为 `LLM_OUTPUT_INVALID`，不自动增加模型调用循环，保留现有人工重试入口。

### 第四批：修复认证和 HTTP 请求生命周期

**CR-005**

- TokenStore 使用单条存储记录保存 `session_id` 与两类 token。
- 登录建立新会话 ID；刷新保留 ID；退出清除记录。跨标签页同步整条记录。
- 每个请求捕获会话 ID，在刷新、重发、返回结果和认证失败清理前核对。
- 旧会话请求结束为取消，不清理新会话，也不改用新身份重发。
- 刷新结果明确区分成功、过期和失败。部署后重新登录一次。

**CR-010、CR-011**

- 请求的超时和取消覆盖首次请求、等待刷新、重试以及 JSON/Blob 完整读取。
- 保持普通读取 15 秒、写入和上传 5 分钟的默认期限；重试不重新获得完整期限。
- 共享 token 刷新使用独立的 10 秒期限。
- 单个请求取消只退出自己的等待；会话退出或切换才取消该会话的共享刷新。
- 定时器和事件监听器在完整操作结束后清理。

### 第五批：修复任务通知和页面异步状态

**CR-007**

- runner 在领取、完成、失败、取消和恢复事务提交后，发布现有格式的任务事件。
- 取消和人工重试的通知也移到事务提交之后。
- 文档详情在解析或切分活动期间每 3 秒刷新一次，终态停止；请求不重叠。
- Redis 通知失败时由轮询完成状态同步。

**CR-008、CR-009**

- WebSocket 建连前通过现有项目访问接口检查权限，复用 HTTP 的刷新机制。
- 保留后端 accept 前拒绝未授权连接的策略；前端不再依赖握手失败传递 4401/4403。
- 权限拒绝停止重连，网络故障继续退避；已经建立连接后的撤权关闭码继续生效。
- 广播只删除确认失效的连接，不用旧快照替换整个连接集合。

**CR-012**

- 候选来源请求、候选列表、导出列表和文档详情请求增加取消及请求序号校验。
- 切换候选时立即清空来源区；只有当前候选对应的响应可以更新内容。
- 来源未加载完成时禁用证据添加和支持性审核提交。

**CR-014**

- 两次同步 MinIO 上传通过 `asyncio.to_thread` 执行。
- 上传前后保留现有取消、租约和发布检查；阻止超时或取消后的数据库发布。

**两个附加问题**

- queued 取消直接返回终态时，仍加载批次汇总并调用一次终态回调。
- 切分按钮为每次新操作生成新幂等键；网络重试复用当前键。请求显式携带当前清洗版本 ID，避免复用旧版本任务。

### 第六批：修复来源页码和导出内容

**CR-015**

- 新建清洗 Section 的可信页码只来自解析器结构化页面或物理页码映射；正文中的 `Page 888` 等文字不参与来源判定。
- 合并清洗版本时冻结来源区间：Section ID、合并文本字符范围、来源页集合及映射是否可信。
- 切分、递归拆分、合并和 overlap 全程携带来源区间，最终按区间计算页码并集。
- Chunk 关联首个实际来源 Section，消除当前统一关联首个文档 Section 的做法。
- 来源未知时保持空页码集合；后续证据和导出如实继承。递增现有 splitter 版本。

**CR-013**

- messages/ShareGPT 的用户输入使用：
  - 无 input：原问题或指令；
  - 有 input：`问题或指令 + "\\n\\n" + input`。
- 保留 input 原文，验证其类型，不静默丢弃。
- formatter 版本递增为 `exporter-v3`；清空旧处理结果后无需保留旧 formatter 分支。

## 3. 接口与数据迁移

集中增加必要字段，沿用现有错误响应格式：

| 位置 | 变更 |
|---|---|
| Candidate 响应 | 增加 `content_revision`、`reviewed_content_revision` |
| 候选编辑、审核、提升请求 | 必填 `expected_revision`；提升接口增加请求体 |
| 409 错误 | 增加 `CANDIDATE_REVISION_CONFLICT`、`DOCUMENT_IN_USE` |
| 生成任务错误 | 增加 `LLM_OUTPUT_INVALID` |
| Section | 增加来源页码映射状态，区分可信映射与未知 |
| 清洗版本 | 增加冻结的来源区间数据 |
| 前端内部认证 | TokenStore 改为包含会话 ID 的整体记录 |

数据库字段通过增量 Alembic 迁移落地；同步更新 OpenAPI、前端生成类型和相关调用。既有迁移链保留，不重新整理成另一套初始化框架。
